## Quirks

- `typer`: an app with a single command collapses into that command; `simagent` defines an
  `@app.callback()` so subcommands always work.
- On Windows, `Path.write_text` writes CRLF. Scripts that generate committed files write with
  `newline="\n"` so `ruff format --check` and staleness tests behave the same on Linux and Windows.

## Material data (Phase 1.1)

- `src/photonsim/data/materials.json` is generated by `scripts/build_materials.py` from NIST
  SRD 126 (Hubbell & Seltzer, X-ray mass attenuation and energy-absorption coefficients),
  for water, polyethylene, ordinary concrete, aluminium, iron and lead, 0.1–10 MeV (18 points
  each, no absorption edges in that range). Densities come from the same database (tables 1–2).
- NIST blocks Python's default `urllib` User-Agent (HTTP 403); the script sends a generic one.
- **Mapping to the simplified model (R-SIM-2):** `mu_total = rho·(mu/rho)`, `mu_abs = rho·(mu_en/rho)`.
  The model absorbs a photon with probability `mu_abs/mu_total` at each interaction and otherwise
  scatters it isotropically with no energy loss. Using the energy-absorption coefficient as the
  absorption probability is an energy-weighted approximation (the fraction of interaction energy
  deposited locally), not a physical event probability. It keeps narrow-beam attenuation exact
  (`mu_total`) while giving a plausible absorbed/scattered split. Transmission includes scattered
  photons, so it is above `exp(-mu_total·x)` (a crude build-up). Documented in the API reference.

## Sandbox (Phase 2)

- **Base image and pins:** `python:3.12.16-slim-bookworm` (tag checked on Docker Hub). The full
  wheel set in `sandbox/requirements.txt` was resolved for cp312/manylinux x86_64 with
  `pip install --dry-run --report --platform … --only-binary=:all:` and is installed with
  `--no-deps` + `pip check`. Version bumps: re-run that resolution, don't hand-edit one pin.
- **Getting `result.json` out:** R-SBX-3 needs a size-limited writable `/out` *and* `--rm`, so
  `/out` is a tmpfs that disappears with the container; `docker cp` after exit is impossible.
  `sandbox/launch.py` (in the image, standard library only) runs the script as a child process,
  then prints `result.json` after a marker line containing a random per-run nonce. The host takes
  the last marker. A script that forges a marker can only fake its own result, which it could do
  with `submit()` anyway, so this adds no new capability. Raw stdout is kept up to ~1.25 MB (tail)
  so a maximal 1 MB result survives, then the visible stdout is capped to 20 000 chars (R-SBX-6).
- **Timeouts:** `subprocess` timeouts only kill the `docker` CLI, not the container, so the
  runner names each container (`simagent-<random>`) and runs `docker kill` on timeout.
- Extra hardening beyond R-SBX-3: `--pull never` (a missing image fails fast instead of pulling),
  `--ipc none`, `--ulimit nofile=256:256`, `noexec,nosuid,nodev` on both tmpfs mounts, swap
  disabled (`--memory-swap` = `--memory`), `python -I -B` (isolated mode).
- `docker` CLI on Windows: Docker Desktop must be able to bind-mount the temp dir
  (`%LOCALAPPDATA%\Temp`, under `C:\Users`, shared by default with the WSL2 backend).
- `SIMAGENT_REQUIRE_DOCKER=1` makes pytest fail (exit 4) instead of skipping Docker tests; CI sets it.
- The policy also blocks numpy's file/native helpers (`np.load`, `np.save*`, `loadtxt`,
  `fromfile`, `memmap`, `ctypeslib`, `f2py`, …), `vars/globals/locals`, `input`, `help`,
  `memoryview`, and format strings that reach dunder attributes. `__name__` stays allowed
  (`if __name__ == "__main__":`, `type(x).__name__`).
- `LocalRunner` passes only a minimal environment (no host variables, so no API keys), plus
  `SYSTEMROOT`/`WINDIR`/`TEMP`/`TMP` on Windows, which Python needs to start.

## Evaluation harness (Phase 5, 2026-11-07)

- **Task set:** 36 tasks (5 per category, 6 ambiguous/misleading). Expected values come only from

  reference stored and checked by a test).
- **Tolerances:** numeric checks use k·√2·σ_ref (k = 4) from the reference run's standard error,

## Sampling settings in results headers (v2 Phase 2.1, 2026-11-09)

- v2 results files start with one header line (`"kind": "header"`): provider, model, Ollama
  digest and quantisation (from `/api/tags`), mode, task set, temperature, seed,
  `seed_supported`, prompt version, attempt budget, output-token cap, code commit (with `-dirty`
  when tracked files are modified). Resuming a file whose header differs on any sampling or
  identity field is refused; the code commit may differ on resume and is also stored per record.
  v1 files have no header and are read as before.
- **Groq seed:** `langchain-groq` 1.1.3 `ChatGroq` has no `seed` field, but the Groq API
  reference (console.groq.com/docs/api-reference, checked 2026-11-09) documents `seed` on chat
  completions: "best effort to sample deterministically", "Determinism is not guaranteed". It is
  passed via `model_kwargs` (verified in `ChatGroq._default_params`). So `seed_supported` is
  `true` for Groq, meaning "accepted", not "reproducible". The fake provider records `false`.

## Statistics (v2 Phase 2.3)

- `src/simagent/evaluation/stats.py`, NumPy + `math` only. Bootstrap: 10 000 resamples over
  tasks, RNG seed 20261109, percentile interval.
- **McNemar reference values** come from Fagerland, Lydersen & Laake (2013), "The McNemar test
  for binary matched-pairs data: mid-p and asymptotic are better than exact conditional", BMC
  Med Res Methodol 13:91, Table 6 ("McNemar exact" row), read from the Europe PMC full text
  (PMC3716987) on 2026-11-09: discordant 1/7 → p = 0.0703; table 59/6/16/80 → p = 0.0525.
  The paper defines the two-sided exact conditional p-value as twice the one-sided tail (1.0

## Provenance trace (v2 Phase 3)

- `photonsim._provenance` records each `simulate()` call and each `sweep()` point only when
  `PHOTONSIM_TRACE=1` is in the environment at import. The sandbox image sets it (`ENV`); the
  launcher runs the script with `python -I`, which ignores `PYTHON*` variables only, so the flag
  survives. `LocalRunner` also sets it, so offline tests get traces (dev only, no isolation).
- `simagent_io.submit()` writes `trace.json` **before** `result.json`, replacing any file the
  script wrote there. The launcher returns it in the envelope (capped at 1 MB like the result);
  a missing or bad trace is a warning, never a failed run. Attempts save it as
  `attempt_N/provenance.json` (`trace.json` was already taken by the run log).
- **What this does and does not protect:** with the policy on, generated code cannot reach `os`
  or the recorder (R-POL-6), so the trace is the simulator's record. With the policy disabled,
  the script controls its own process: overwriting at `submit()` defeats a fake file written
  before `submit()` (the R-TRACE-3 test), but a script could still rewrite `/out` after `submit()`
  or alter the recorder in memory. It could equally forge `result.json`, so this is the same trust
  boundary as v1: the policy is the defence, the sandbox limits the damage.
- Image tag bumped to `simagent-sandbox:2` so a stale image without tracing fails fast ("not
  built") instead of silently returning no trace.

## Verifier (v2 Phase 4)

- **Request facts** (`request_facts.py`): besides the R-REQ-1 list, a `derived` flag marks
  requests for ratios, factors, differences, changes, fits or slopes, so V-RANGE and V-TRACE do
  not treat such answers as simulated fractions. Steps ("in 0.5 cm steps", "whole centimetres")
  are attached to a range in the same sentence and are not counted as stated thicknesses.
- **Checks narrowed during design, before any reference was run** (general rules, not per task):
  - V-SWEEP: a 2-value list or a range without a step is not a sweep (e.g. "when the energy goes
    from 1 MeV to 2 MeV" names two energies); a search ("smallest thickness ...", "lowest
    energy ...") may stop early, so the "fewer than 3 distinct values" rule is skipped for
    searches. The stacking rule (one call whose total thickness is the sum of the sweep values)
    always applies.
  - V-RANGE and V-TRACE only apply when the answer is a fraction (requested quantity is
    transmitted/reflected/absorbed and not `derived`). V-TRACE only applies when the trace holds
    exactly one configuration and is not truncated.
  - V-LENGTH compares every simulated thickness with the stated singles, lists and ranges, which
    also catches the v1 failure where a 1-10 cm sweep was stacked into one 55 cm slab.
- **R-VER-3:** all 32 runnable dev references pass with zero `fail` findings, both on the stored
  traces and in a fresh Docker run (`tests/test_verify_references.py`). **No check had to be
  narrowed after running references.** The verifier was not run on held-out references (R-HO-5).

## Block 6.1 first start: Docker Desktop refused every container (2026-11-10)

- **What happened:** `ollama-qwen2.5-coder_3b-p3-baseline-dev-s0` recorded its first 13 tasks
  as `status failed, no result to check`. Every attempt's stderr was
  `docker: Error response from daemon: Access is denied.` (exit 125, run_s about 0.08 s), so no
  script ever ran. The model replies were normal.
- **Where it came from:** the Docker Desktop backend log shows each `containers/create`
  rejected on the Windows side within about 2 ms, before the bind-mount approval step that a
  working create reaches. Docker Desktop had just been resumed from Resource Saver (idle 9 h,
  resumed at 01:38 UTC; failures 01:39:43-01:40:58). The same message is reproduced exactly by
  bind-mounting a directory that the user cannot read, so Docker Desktop could not read the
  sandbox's temp script directory. The trigger is not pinned down: by 01:42 UTC the same image,
  TEMP folder and code ran normally, and nothing in the Windows event logs covers it.
- **Code defect (fixed in `fix(runner)`):** the runner returned exit 125 as the script's exit
  code, and the harness's catch-all would have recorded even a `RunnerUnavailableError` as a
  failed task, so `--resume` kept the bad rows. Now exit 125 without the launcher envelope raises
